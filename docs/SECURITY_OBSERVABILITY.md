# Request audit and CORS

SEC-05 adds independent provider attempt/completion events to cover late
responses after HTTP disconnection and safe metadata on provider HTTP errors.
See [provider reconciliation](PROVIDER_USAGE.md). Do not add their operation
counts to those in HTTP audit events: they describe the same provider request.

This change implements the first backend delivery of the security plan: controlled
CORS rejections and safe request/provider diagnostics. It does not change the
allowed origins, analysis quotas, proxy trust configuration, or Cloudflare rules.

## Behavior

- An untrusted Origin receives HTTP 403 with `code: CORS_ORIGIN_DENIED` for actual
  requests and preflights, before controllers or external providers run.
- Requests without Origin retain their existing behavior. CORS is a browser
  policy, not authentication or a replacement for Turnstile/rate limiting.
- `X-Request-ID` is generated by the server for each request, including failures.
  Incoming IDs are not trusted. Allowed browsers can read the response header.
- A `RequestAudit` event is emitted once on response completion or disconnect.
  Disconnects use a diagnostic status 499, not a response sent to the client.
- Existing public detector error statuses and codes remain in use. A malformed
  Sightengine response retains its intended generic service-unavailable message.

## Log fields and privacy

The JSON message contains `event`, UTC `timestamp`, `environment`, `requestId`,
`method`, canonical `route`, HTTP `status`, `durationMs`, and `category`.
Optional `providerRequestId` and `operations` come from the provider response;
IDs must match a bounded identifier format and operations must be nonnegative
safe integers. These fields may exist even when the provider response cannot
produce a valid analysis result. A timeout may have consumed provider operations
without returning these fields. Do not sum only successful HTTP responses and
present that as an exact provider invoice.

Only `/detect/ai`, `/affiliate/ugee/random` and `/health` are recorded as routes;
other paths become `other`. Logs exclude query strings, Origin, user-agent, IP,
request headers/bodies, file names, images, tokens, credentials and raw exceptions
or provider response bodies. Existing platform HTTP logs are separate and can
still contain client metadata; this change does not alter platform retention.

Categories distinguish CORS, validation, short/daily rate limits, missing/invalid
Turnstile challenges, provider configuration, timeouts, network/HTTP failures,
Sightengine authentication/quota/malformed response, and successful analysis.
Other HTTP failures receive a bounded generic category. Unknown internal failures
must not be treated as conclusively diagnosed by a previous validation stage.

Environment is selected from `APP_ENV` or Railway's `RAILWAY_ENVIRONMENT_NAME`,
using only `production`, `staging`, `qa`, `development`, or `test`.
Without an explicit recognized label, a production build reports `unknown`;
otherwise local execution reports `development` (`test` under Jest).
`NODE_ENV=production` alone never identifies a Railway QA build as production.
`APP_ENV` is optional, not a secret; prefer Railway's automatic environment name
unless an override is necessary. Confirm the emitted value before release.

No database, tracing exporter or additional log destination is introduced. Events
go through the existing Nest logger/stdout and the hosting log retention policy.
Before rollout, record the effective Railway retention/access policy; do not
export logs indefinitely or claim a retention period this code does not enforce.

## Verification

Run `npm test -- --runInBand`, `npm run test:e2e -- --runInBand`,
`npx eslint "{src,test}/**/*.ts"` and `npm run build`.
Integration tests use actual Nest/Express/Multer/throttling and file signatures;
external providers are simulated. They check CORS, provider error categories,
concurrent request isolation, safe log fields and existing retry/session behavior.

For manual local review, start the API with `APP_ENV=development`, `PORT=3001`
and a local session secret separate from QA/production. Start the frontend with
`NEXT_PUBLIC_API_BASE_URL=http://localhost:3001` and a development public app
environment. Use the approved project workflow for review and local/QA signoff.
Uploading real images with real provider credentials consumes the shared quota.

PowerShell smoke checks (no external provider calls):

```powershell
curl.exe -i http://localhost:3001/health
curl.exe -i -X OPTIONS http://localhost:3001/detect/ai -H "Origin: https://untrusted.example" -H "Access-Control-Request-Method: POST"
curl.exe -i -X POST http://localhost:3001/detect/ai -H "Origin: https://untrusted.example"
curl.exe -i -X OPTIONS http://localhost:3001/detect/ai -H "Origin: http://localhost:3000" -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: x-bot-session-token"
```

Expect 200, 403, 403, and 204 respectively. Match each `X-Request-ID` to the local
audit event. A rejected origin does not receive Access-Control-Allow-Origin;
browser JavaScript cannot read that cross-origin response, which is intentional.

Rollback is a revert of this backend delivery through the project's deployment
workflow. No Cloudflare or variable changes are required to undo the code.
